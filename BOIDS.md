# Экспериментальный контроллер локальных правил Boids

## Статус и источник

Это **не** изменение APF A-1.0.0. Отдельный, неизменяющий базовые методы компонент
`src/swarm_apf/boids.py`, идентификатор `BOIDS-EXPERIMENT-1.0.0`.

Первоисточник: Craig W. Reynolds, *Flocks, Herds, and Schools: A Distributed
Behavioral Model*, SIGGRAPH '87, pp. 25–34,
https://doi.org/10.1145/37401.37406 .
Авторский обзор трёх правил: https://red3d.com/cwr/boids/ .

Оригинальные Boids — анимационная модель с steering behaviors; ниже **наша
упрощённая кинематическая адаптация** для E1, а не точное повторение формул
оригинала. Новизна этих трёх правил **не заявляется**.

## Интерфейс и локальность

```python
from swarm_apf.boids import BoidsController, BoidsParameters
controller = BoidsController(BoidsParameters())
terms = controller.forces(observation)       # диагностика компонент
heading = controller.direction(observation) # нормированное направление
u = controller.command(observation)          # скорость для E1
metadata = controller.metadata()              # сохранять рядом с результатами
```

Используются только `observation.self_position`, `goal` (либо `goal_i`),
`self_velocity`, `robot_radius`, `dt`, `max_speed`, `neighbors` и, **только при
`w_obstacle>0`**, `obstacles`. Каждый сосед содержит `relative_position`, а
для alignment — либо абсолютную `velocity`, либо `relative_velocity` относительно
робота i. Для вырожденных совпадений центров по возможности используются
локальные `robot_id` и ID соседа. Чужие цели, глобальные позиции/карта,
статистика и будущие команды не читаются.

E1 должен передавать соседей только в своём `neighbor_radius`. Контроллер
дополнительно отбрасывает тех, кто находится дальше `interaction_radius`.
При `w_alignment>0` и отсутствии скорости хотя бы у одного учитываемого соседа
возникает явная ошибка: выдумывать «скорость» по одному снимку нельзя.

## Точное определение векторов

Обозначим `r` — радиус робота, `d_ij=||p_j-p_i||`,
`s_ij=d_ij-2r`, `R=interaction_radius`,
`d_s=separation_clearance` (именно **зазор** между поверхностями),
`N_i` — видимые соседи с `d_ij<=R`.

- `G_i = unit(g_i-p_i)`.
- Для соседей `s_ij<d_s`: `S_i = mean[unit(p_i-p_j) * clamp((d_s-s_ij)/d_s,0,1)]`;
  при пустом множестве `S_i=0`.
- `C_i = cap_norm(mean[p_j-p_i]/R, 1)`; при `N_i=∅` это ноль.
- `L_i = cap_norm((mean[v_j]-v_i)/v_max,1)`; при `N_i=∅` это ноль.
- Отдельное **не-boids** препятственное steering `O_i` (выключено по
  умолчанию): для видимого круга с относительным центром `z_k`, радиусом
  `R_k` и зазором `s_k=||z_k||-r-R_k`, если `s_k<obstacle_clearance`,
  добавить `-unit(z_k) * clamp((obstacle_clearance-s_k)/obstacle_clearance,0,1)`;
  усреднить активные вклады, иначе ноль.
- `F_i = w_goal*G_i + w_separation*S_i + w_cohesion*C_i +
  w_alignment*L_i + w_obstacle*O_i`.
- `u_i = unit(F_i) * min(max_speed, ||g_i-p_i||/dt)`, но если сила
  вырождается или цель достигнута в пределах `goal_stop_radius`, то `u_i=0`.

`unit(0)=0`; `cap_norm(x,1)=x/max(1,||x||)`; при совпавших
центрах ID задают противоположные запасные оси, если ID доступны, иначе
вклад separation равен нулю. Коллизии всё равно контролирует E1.

Ни один из `G,S,C,L,O,F` не является силой в ньютонах, а команда скорости
не является ускорением. Синхронный физический шаг E1 не изменяется.

### Откуда брать скорость, если физическая динамика не моделируется

Пользуемся уже опубликованным контрактом E1 `Observation.self_velocity` и
скоростями соседей. Скорость на шаге `t` должна быть
`v_i(t)=(p_i(t)-p_i(t-dt))/dt` **только по принятым состояниям**.
После `reset`: `v_i=0`; после отклонённого из-за коллизии предложения
скорость и позиция не перезаписываются. В E1, согласно `ARCHITECTURE.md`,
уже существуют массивы `velocities`, а контроллер получает локальные
скорости. Новую физическую степень свободы добавлять не надо.

### Начальные значения (не оптимальные)

| Параметр | Значение | Интерпретация |
|---|---:|---|
| `w_goal` | 1.0 | Индивидуальная цель |
| `w_separation` | 2.0 | Предотвращение скучивания, без гарантии безопасности |
| `w_cohesion` | 0.35 | Притяжение к локальному среднему |
| `w_alignment` | 0.35 | Согласование наблюдаемых направлений/скоростей |
| `w_obstacle` | 0.0 | **Отключено**, чтобы не маскировать вклад Boids |
| `separation_clearance` | 0.75 | Порог по зазору роботов |
| `interaction_radius` | 2.5 | Максимальное расстояние до центра соседа |
| `obstacle_clearance` | 1.2 | Порог видимого зазора до препятствия |
| `goal_stop_radius` | 0.0 | Ноль скорости лишь в точке цели |

Значения являются стартовой конфигурацией, а не результатами настройки.
Для полноты сенсорного охвата необходимы
`interaction_radius <= neighbor_radius`,
`separation_clearance+2r <= neighbor_radius`,
`obstacle_clearance <= obstacle_sensor_radius` при `w_obstacle>0`.
Если дальность меньше — информация остаётся локально усечённой.

## Интеграция в *реальный* E1

1. Скопировать **только** `src/swarm_apf/boids.py` и
   `tests/test_boids.py` в существующий проект E1+A; не заменять
   существующие `models.py`, `physics.py`, `sensing.py`, `swarm.py` и
   `multi_apf.py`.
2. Там, где E1 ранее получал `APFController`, передать экземпляр
   `BoidsController` через **тот же существующий интерфейс `command(obs)`**.
   Точный синтаксис конструктора `SwarmSimulator` не приводится, потому что
   его исходник не входит в этот набор вложений.
3. Убедиться, что реальный `NeighborObservation` имеет поле `velocity`
   **или** `relative_velocity`. Если используется иное имя — написать
   однозначный адаптер на уровне `sensing.py` и добавить интеграционный
   тест. Не заменять отсутствие измерения нулевой скоростью молча.
4. Проверить, что реальный E1 сохраняет в `summary.json` возвращаемые
   `controller.metadata()` и `stage=BOIDS_EXPERIMENT`.
5. Выполнить полный `pytest` с E0/E1/A golden tests, проверить SHA-256
   `multi_apf.py` по сохранённому `baseline_A.lock.json` **в оригинальном
   дереве**. Только затем запускать 5/10-роботные сцены, сохранять полный
   `history.csv`, `summary.json`, `trajectory.png` с отличающимся префиксом.

## План сравнения: НЕ результаты

В каждой сцене (одинаковые позиции, цели, радиусы, dt, дальность видимости)
отдельно запускать: `Goal-only` (`w_goal>0`, все остальные веса ноль),
`Goal+S`, `Goal+S+C`, `Goal+S+C+L`, `Goal+S+C+L+O` и замороженный `A-1.0.0`.
В экспериментах с препятствиями для исследования *чистого вклада* S/C/L
держать `w_obstacle` **одним и тем же** у Boids-вариантов (например, включён
во всех); отдельно запускать с `w_obstacle=0` как проверку ограничений.

Предлагаемые сцены: (1) пять роботов в свободной плоскости, общая область
движения, индивидуальные цели; (2) десять роботов, пересекающиеся маршруты;
(3) один круг на маршруте; (4) узкий коридор, где сильная cohesion может
мешать проходу; (5) расходящиеся индивидуальные цели, чтобы выявить конфликт
сплочённости и достижения цели. При необходимости добавить N=20 и
несколько независимо сгенерированных seed **только для построения сцен**.
Контроллер seed и карту целиком не получает.

Отчётные метрики: доля успешных запусков по внешним seed, факт/число
`COLLISION_*`, число попыток, время достижения **всех** целей, принятые
длины путей, минимум непрерывного зазора включая rejected segment,
доля зависших/таймаутов, средняя локальная дистанция и согласование
направления у движущихся соседей. Никакие численные сравнения до
фактических запусков не утверждаются.

## Потенциальные ограничения

- Separation не гарантирует отсутствия пересечений за `dt`.
- Cohesion может противодействовать индивидуальным целям и мешать проходу
  в коридоре; Boids **не равнозначен** formation control.
- Alignment из дискретных перемещений может быть скачкообразным при
  остановках/поворотах; у нулевых начальных скоростей он равен нулю.
- Локальность ограничивает дальность и допускает распад на подгруппы.
- Без явного препятственного steering контроллер препятствий не избегает.
- Даже с obstacle steering у него нет ни гарантии безопасности, ни
  гарантии достижения целей. Фиксацию реальных столкновений сохраняет E1.
